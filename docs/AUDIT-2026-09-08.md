## High

### H-1 · PostCSS bundled in Next.js — severity escalation from L-1

**Files:** `package.json`, `package-lock.json`

The `postcss` module bundled inside `next` now carries **HIGH**-severity
advisories (previously tracked as L-1 moderate). Four CVEs are now reported:

| CVE | Description |
|---|---|
| GHSA-qx2v-qp2m-jg93 | XSS via unescaped `</style>` in CSS stringify output |
| GHSA-6g55-p6wh-862q | Arbitrary file read via attacker-controlled `sourceMappingURL` |
| GHSA-fxqj-rqcc-2cmp | Incomplete fix of GHSA-6g55-p6wh-862q — `.map` file disclosure when `from` unset |
| GHSA-r28c-9q8g-f849 | Path traversal via `sourceMappingURL` auto-loading |

**Context:** These affect the Next.js build toolchain's internal CSS
processing — not the app's CSS served to end users at runtime. Production
builds on Vercel are not directly exploited through these vectors. The risk
is to anyone with write access to CSS source files processed by the bundled
postcss during CI/build.

**Fix:** Upgrade to `next@16` which bundles a patched postcss. This is a
breaking change (`next@16` requires review of App Router, config, and
middleware APIs). Track on the next planned major-version upgrade cycle.
`npm audit fix --force` would apply it automatically but risks breaking the
build.

## Medium

### M-2 · No rate limiting on expensive API routes — carry-over

**Files:** `src/app/api/spotify/sync-playlist/route.ts`,
`src/app/api/practice/generate-station/route.ts`

No rate-limiting middleware exists. Two routes make expensive third-party
calls on each request with no throttle:

- `POST /api/spotify/sync-playlist` — in the worst case (13 players with no
  walk-on songs, a full default-pool search cycle) makes up to 13 × 15 = 195
  sequential Spotify search calls in a single request.
- `POST /api/practice/generate-station` — proxies every call to the
  Anthropic API, incurring cost and latency per request.

Both can be triggered by any approved coach with no per-user or per-IP
throttle.

**Fix:** Add per-user rate limiting via `@upstash/ratelimit` with Vercel KV.
Suggested limits: sync-playlist 5 req/min, generate-station 10 req/min,
read-only roster/history endpoints 60 req/min.

### M-3 · Logo data-URL accepted with no server-side size cap — carry-over

**File:** `src/app/api/roster/route.ts` (PUT handler, `config?.logoDataUrl`
path, ~line 112)

Team logos stored as base64 data URIs have no server-side size limit. The
Onboarding UI caps file selection at 2 MB client-side, but the API itself
enforces nothing — a direct API caller can upload an arbitrarily large logo.
A large value bloats the `teams.logo_data_url` column and can exceed Neon's
request payload limit (64 MB), causing 500 errors for all subsequent reads
of that team.

**Fix:** Reject `logoDataUrl` values whose string `length` exceeds ~270 000
characters (~200 KB binary, typical cap for a thumbnail). Return HTTP 413.

### M-4 · `constraint_overrides` table is completely unused — carry-over

**Files:** `src/lib/schema.ts`, `drizzle/0001_multi_team.sql`

The `constraint_overrides` table exists in schema and migrations but is
never queried by any route or UI component. It is dead weight at the DB
layer.

**Fix:** Drop the table in a new migration (`drizzle/0006_drop_constraint_overrides.sql`)
and remove `constraintOverrides` from `src/lib/schema.ts`. Or wire it into
the solver's constraint pipeline if the feature is actively planned.

### M-5 · AI model ID hardcoded in source — carry-over

**File:** `src/app/api/practice/generate-station/route.ts:86`

`claude-haiku-4-5-20251001` is a literal string in the route handler. When
Anthropic retires the model ID, the endpoint silently returns 502 errors with
no obvious signal to operators. There is no equivalent of the `check:models`
script used in the sibling `escape-hatch-explore` project.

**Fix:** Extract the model ID to a named constant in `src/lib/ai.ts`. Add a
weekly CI step (or `npm run check:models` script) that calls the Anthropic
models list endpoint and verifies the constant is still active.

### L-2 · No Content Security Policy header — carry-over

**File:** `next.config.ts`

The app sets `X-Frame-Options`, `X-Content-Type-Options`, and `Referrer-Policy`
but no CSP. User-supplied content (team names, player names, logo data URIs)
is rendered in the DOM. Any future `dangerouslySetInnerHTML` path would
create an XSS vector with no CSP backstop.

**Fix:** Add a CSP via `next.config.ts` headers:
```
default-src 'self';
img-src 'self' data: https://i.scdn.co https://mosaic.scdn.co;
script-src 'self' 'unsafe-inline';
connect-src 'self' https://api.spotify.com;
```
Tighten further as content sources are fully inventoried.

### L-4 · No test suite — carry-over

**Files:** `src/lib/scheduler.ts`, `src/lib/constraints.ts`

The backtracking scheduler and constraint logic are pure functions with
complex conditional behaviour but have zero test coverage. An edge-case
constraint change could silently produce invalid game sheets.

**Fix:** Add `vitest` and cover: bench schedule selection (10/11/12/13
players), playoff mode bench ordering (top-6 off bench in final inning),
avoid-positions post-pass, `validateGameSheet` violation detection.

### Fix 1 — fflate CVE: 0.8.2 → 0.8.3 via `npm audit fix`

**File:** `package-lock.json`

GHSA-px8p-9vwx-vf98 (moderate): `fflate` ≤ 0.8.2 can enter an infinite loop
when parsing malformed ZIP64 archives. Affects `jsPDF` (PDF export feature).
`npm audit fix` bumped `fflate` from 0.8.2 to 0.8.3 which contains the fix.
This was a new finding not present in the 2026-09-01 audit.

### Fix 2 — Admin PATCH email conflict returns 500 instead of 409

**File:** `src/app/api/admin/users/route.ts` (PATCH handler)

The `db.update(users)...returning()` call in the admin PATCH route had no
try-catch. When an admin attempted to set a user's email to one already in
use by another account, Postgres raised a unique constraint violation (code
23505) that propagated as an unhandled 500 error — while the POST (create
user) handler already caught 23505 and returned a proper 409. Applied the
same guard to the PATCH handler via a locally-scoped `doUpdate()` async
function, keeping TypeScript's return-type inference intact.

```typescript
// before: no try-catch — DB error propagated as 500
const [updated] = await db.update(users)...returning({...});

// after: 23505 → 409 Conflict
let updated: ... | undefined;
try {
  [updated] = await doUpdate();
} catch (err: unknown) {
  if (err && typeof err === "object" && "code" in err && err.code === "23505") {
    return NextResponse.json({ error: "Email already in use by another account" }, { status: 409 });
  }
  throw err;
}
```
