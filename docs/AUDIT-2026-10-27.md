## Carry-forward findings (escalations and status)

### SECURITY

#### **High** — M-1 (escalated from Medium): AI model ID is 13 months old

**File:** `src/app/api/practice/generate-station/route.ts:86`  
**First flagged:** AUDIT-2026-08-11 (Low); escalated to Medium AUDIT-2026-10-20; escalated to **High** this week.  
**Description:** `claude-haiku-4-5-20251001` (released 2025-10-01) has been the hardcoded model for 13 months with no update. Anthropic retires models without guaranteed advance notice; the sibling project CLAUDE.md documents a real retirement (`claude-sonnet-4-20250514`) that caused silent 404s in production for over a month. No `check:models` script exists in this project. If this model is retired, `/api/practice/generate-station` silently returns HTTP 502 with no alerting. With 13 months of age and a newer generation now available (`claude-haiku-5-5`), the retirement probability this cycle is material.  
**Recommended fix:**
1. Verify `claude-haiku-4-5-20251001` is still live via the Anthropic API (check models endpoint — no credits needed).
2. Update to `claude-haiku-5-5`. Confirm JSON-output behaviour is unchanged (the route parses structured JSON from the model). Note: newer Haiku models do not think by default, but verify `max_tokens: 600` is still appropriate.
3. Add a `check:models` npm script (follow the pattern in `escape-hatch-explore`).  
**Not auto-applied:** model generation changes require manual API verification before pushing to production.

#### Low — S-1 (carry-forward from AUDIT-2026-10-20): `spotify-status` endpoint missing approval gate

**File:** `src/app/api/auth/spotify-status/route.ts:14`  
**Priority:** Low  
**Description:** The endpoint checks `getUserId()` (session valid?) but not `user.status === "approved"`. A `pending` or `suspended` user with a valid session can call it and discover whether the service-account Spotify integration is configured and linked. The returned data (`configured`, `linked`) is app-level config, not user data — so the exposure is minimal. But the inconsistency with every other data-touching route is a pattern gap.  
**Recommended fix:**
```ts
const user = await getUser(request);
if (!user || (user.status !== "approved" && user.role !== "admin")) {
  return NextResponse.json({ configured: false, linked: false }, { status: 403 });
}
```

#### Low — L-2 (carry-forward since AUDIT-2026-10-06): Dead code — `getValidAccessToken` + legacy per-coach Spotify routes

**File:** `src/lib/spotify.ts:182–215`; `src/app/api/auth/spotify-connect/route.ts`; `src/app/api/auth/spotify-callback/route.ts`  
**Priority:** Low  
**Description:** `getValidAccessToken(userId)` is exported but imported by no route. The per-coach callback still writes `spotifyAccessToken` / `spotifyRefreshToken` to `users` but nothing reads them for outbound calls. Dead code inflates surface area.

#### Medium — P-1 (carry-forward since AUDIT-2026-09-01): No rate limiting on expensive third-party endpoints

**Files:** `src/app/api/spotify/sync-playlist/route.ts`; `src/app/api/practice/generate-station/route.ts`  
**Priority:** Medium  
**Description:** Both routes call paid external APIs (Spotify, Anthropic) without per-user throttling. A tight loop by an approved coach generates unbounded cost.  
**Recommended fix:** Store last-called timestamp per user (DB or Vercel KV) and return HTTP 429 if called more than once per 10 seconds per user.
