## Medium

### M-2 · No rate limiting on any API route — carry-over
**Files:** `src/app/api/**`
**Finding:** No rate-limiting middleware exists. Every API route is exposed
to unlimited request volume. The scheduler solver endpoint is particularly
vulnerable — it runs CPU-intensive backtracking synchronously on the server.
**Fix:** Add per-IP or per-user rate limiting (e.g. Vercel's `@vercel/kv`
sliding-window, or `upstash/ratelimit`). The solver endpoint should have a
lower limit than read endpoints.

### M-3 · Logo data-URL accepted with no size cap — carry-over
**File:** `src/app/api/roster/route.ts` (PUT handler, `logoDataUrl` field)
**Finding:** Team logos are accepted as base64 data URIs with no maximum
size check. An oversized upload bloats the database row and can exceed
Postgres's row-size limits or Neon's request payload cap.
**Fix:** Reject `logoDataUrl` values exceeding ~200 KB (roughly a 150 KB
image after base64 encoding overhead).

### M-4 · `constraint_overrides` schema column is dead code — carry-over
**File:** `src/lib/schema.ts`, `src/lib/scheduler.ts`
**Finding:** The `constraint_overrides` column is defined in the schema and
present in roster PUT, but is never read during scheduling. The solver
ignores it entirely.
**Fix:** Either wire the overrides into the solver's constraint pipeline, or
drop the column to avoid schema drift.

### M-7 · AI model ID hardcoded — carry-over
**File:** `src/lib/ai.ts` (or equivalent)
**Finding:** `claude-haiku-4-5-20251001` is hardcoded. Haiku 4.5 is the
current stable model, so this is not an immediate problem, but the model ID
should live in a central config constant (like `lib/routing-policy.ts` in
Explore) so it can be updated in one place when a new version ships.
**Fix:** Extract to a `MODEL_ID` constant; add a weekly CI check analogous
to `npm run check:models` in Explore.

## Low

### L-2 · No Content Security Policy header — carry-over
**File:** `next.config.js` / `src/middleware.ts`
**Finding:** No CSP header is set. The app serves user-supplied content
(team names, player names, logo data URIs) which could be used to inject
scripts via XSS if any rendering path uses `dangerouslySetInnerHTML`.
**Fix:** Add a restrictive CSP via `next.config.js` headers or middleware.

### L-3 · `storage.ts` references deprecated Vercel Edge Config path — carry-over
**File:** `src/lib/storage.ts`
**Finding:** The module references a Vercel Edge Config pattern that was
superseded. The file appears to be dead — no routes import it.
**Fix:** Delete the file or replace with the current Vercel KV / Blob
pattern if persistence is needed.

### L-4 · No test suite — carry-over
**Status:** Not fixed. `src/lib/scheduler.ts` is a pure backtracking solver
that is exceptionally well-suited to unit testing.
**Fix:** Add `vitest` and cover the scheduler with constraint scenarios:
minimum minutes, max per week, conflict avoidance.

### L-7 · `/api/admin/users` returns unbounded result set — carry-over
**File:** `src/app/api/admin/users/route.ts`
**Finding:** The admin users list runs `SELECT *` with no `LIMIT`. As the
users table grows this response grows without bound.
**Fix:** Add cursor-based pagination (default page 50).

### L-8 · `/api/spotify-status` leaks `serviceUserId` — carry-over
**File:** `src/app/api/spotify-status/route.ts`
**Finding:** The response includes the `serviceUserId` (the internal
Spotify service-account user ID). This is not sensitive on its own, but
leaking internal IDs to clients is unnecessary and reduces the attack
surface of future Spotify API misuse.
**Fix:** Omit `serviceUserId` from the response body.

### L-9 · DELETE handler fetches full row before deleting — carry-over
**File:** `src/app/api/roster/route.ts` (DELETE handler)
**Finding:** The handler fetches the entire roster row (including large
`logoDataUrl`) to verify ownership, then issues a separate DELETE. The
`logoDataUrl` blob is read into memory unnecessarily.
**Fix:** Use `SELECT id, user_id` (ownership check only), then DELETE.

### L-10 · Edge middleware HMAC comparison is not constant-time — NEW
**File:** `src/middleware.ts` (lines ~44–47)
**Finding:** The HMAC session cookie verification compares bytes in a loop
that iterates only `min(len1, len2)` and short-circuits on the first
mismatch. This is a textbook timing-oracle vulnerability: an attacker can
distinguish a forged token that shares a long prefix from one that does not,
leaking information about the real HMAC byte-by-byte.
**Fix:** Use `crypto.subtle.timingSafeEqual` (available in Edge Runtime) for
the final comparison:
```ts
const valid = a.byteLength === b.byteLength &&
  crypto.subtle.timingSafeEqual(a, b)
```
(Note: `crypto.timingSafeEqual` is the Node.js API; `crypto.subtle.timingSafeEqual`
is the Web Crypto API available in Edge runtime.)
