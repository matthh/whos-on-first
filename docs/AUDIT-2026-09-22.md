## Findings

### M-1 · No server-side size cap for `logoDataUrl` — Medium

**File:** `src/app/api/roster/route.ts` lines 112–114

```ts
if (config?.logoDataUrl !== undefined) {
  teamUpdates.logoDataUrl = config.logoDataUrl;
```

The `Onboarding.tsx` component enforces a 2 MB client-side cap (`MAX_LOGO_SIZE`), but the server imposes none. A direct `PUT /api/roster` with an arbitrarily large `logoDataUrl` string will be written to the DB. Large rows can cause performance degradation and may hit Neon row-size limits.

**Recommended fix:** In the `PUT` handler, after the `config !== undefined` type check, add:

```ts
if (config?.logoDataUrl !== undefined && config.logoDataUrl !== null) {
  // ~2 MB binary ≈ 2.75 MB base64 string. Cap with 10% headroom.
  if (typeof config.logoDataUrl !== "string" || config.logoDataUrl.length > 3_000_000) {
    return NextResponse.json({ error: "Logo too large (max ~2 MB)" }, { status: 400 });
  }
}
```

This was listed as tech debt #1 in ARCHITECTURE.md. This audit elevates it to a concrete code recommendation with an exact fix.

### L-1 · Google profile name stored without HTML sanitization — Low

**File:** `src/app/api/auth/google-login-callback/route.ts` lines 95, 124–125, 130–136

When a new user is created or an existing account is linked via Google OAuth, `profile.name` is stored directly:

```ts
const name = profile.name || null;
// …
.values({ email, name, role: "user", status: "pending", … })
```

All other write paths that touch `users.name` — admin PATCH (`route.ts` lines 156–159) and roster PUT `coachName` — strip HTML tags and cap at 100 characters. The Google path does not. XSS from a stored name is low-risk in practice because React escapes output by default, and no route renders names as raw HTML. But the inconsistency is a maintenance hazard: any future route that renders the name unsafely would be silently vulnerable.

**Recommended fix:** Apply the same sanitization used in admin PATCH:

```ts
const name = profile.name
  ? profile.name.replace(/<[^>]*>/g, "").slice(0, 100) || null
  : null;
```

Apply this to both the new-user branch (insert) and the existing-user re-link branch (update).

### L-2 · Spotify search query has no length cap — Low

**File:** `src/app/api/spotify/search/route.ts` line 42

```ts
const q = new URL(request.url).searchParams.get("q")?.trim();
```

`q` is forwarded to Spotify's API without a length limit. A very long query would result in a large URL sent outbound; Spotify would likely return 400/414 but the server absorbs the full round-trip. Low risk given the route is auth-gated.

**Recommended fix:**
```ts
if (!q || q.length > 300) return NextResponse.json({ tracks: [] });
```

### L-3 · `getValidAccessToken` is dead exported code — Low

**File:** `src/lib/spotify.ts` lines 182–215

`getValidAccessToken(userId: number)` is exported but never imported by any route or component. It belongs to the legacy per-coach OAuth token-refresh path — the service-account path (`getValidServiceAccessToken`) handles all actual API calls. The per-coach callback (`spotify-callback/route.ts`) still writes tokens to `users` but nothing reads them for outbound calls.

The function's logic is correct, but exporting dead code is a maintenance burden and creates the impression that per-coach tokens are in active use.

**Recommended fix:** Remove `getValidAccessToken` from `lib/spotify.ts`. If the per-coach OAuth flow is to be fully retired, also remove `/api/auth/spotify-connect` and `/api/auth/spotify-callback` — but that is a larger scope change and should be tracked separately.

## No-change areas

The following audited areas had no new findings:

- **Auth / session flow** — HMAC token creation, cookie options (`httpOnly`, `secure`, `sameSite: lax`), middleware x-user-id stripping and injection all correct.
- **Admin action tokens** — HMAC-signed with 7-day expiry, expiry checked before DB write, HTML properly escaped in response page.
- **Data ownership** — every DB query scopes to `userId` + `teamId` from the verified session header.
- **History POST validation** — players array length capped at 20, shape-checked, date length capped.
- **Admin GET** — column projection excludes Spotify tokens; `.limit(500)` applied.
- **Team DELETE** — COUNT(*) check prevents last-team deletion.
- **Spotify sync** — approval gate present; service account path only; roster mutation is scoped to `(userId, teamId)`.
- **Practice generate-station** — approval gate present; inputs capped (name 80, description 800); Claude response validated before forwarding.
