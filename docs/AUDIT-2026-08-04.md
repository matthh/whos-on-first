## Medium

### M-2 · No rate limiting on expensive third-party routes — carry-over
**Files:** `src/app/api/practice/generate-station/route.ts`,
`src/app/api/spotify/sync-playlist/route.ts`
**Status:** Not fixed. Both routes make outbound calls (Anthropic / Spotify)
without any per-user or global throttle. An approved user can call them in a
rapid loop.
**Fix:** Add Vercel KV or an in-memory TTL counter (e.g. max 10 calls per user
per minute for generate-station, max 5 per minute for sync-playlist). Until KV
is wired up, a `Date.now()`-based cooldown in a module-level `Map` provides a
serverless-safe approximation for low-traffic deployments.

### M-3 · `logoDataUrl` stored without server-side size cap — carry-over
**File:** `src/app/api/roster/route.ts` (PUT handler, `config?.logoDataUrl`)
**Status:** Not fixed. Any base64 image payload can be written directly to
Postgres. The Onboarding UI caps uploads at 2 MB, but direct API calls bypass
this.
**Fix:** In the PUT handler, after extracting `config.logoDataUrl`, reject
strings longer than ~2,750,000 chars (~2 MB binary → base64 overhead):
```typescript
if (config?.logoDataUrl && config.logoDataUrl.length > 2_750_000) {
  return NextResponse.json({ error: "Logo too large (max 2 MB)" }, { status: 413 });
}
```

### M-4 · `constraint_overrides` table is dead code — carry-over
**Files:** `src/lib/schema.ts:77-83`, `drizzle/` migrations
**Status:** Not fixed. The table is created and migrated but is never read or
written by any route or UI component.
**Fix:** Add a new Drizzle migration to drop the table; remove the
`constraintOverrides` export from `schema.ts`.

### M-7 · AI model ID is hardcoded and may go stale — NEW
**File:** `src/app/api/practice/generate-station/route.ts:81`
**Status:** New finding.
**Detail:** `model: "claude-haiku-4-5-20251001"` is the sole model ID in this
project, hardcoded in one place with no accompanying `check:models` script or
any other freshness guard. The sibling project (`escape-hatch-explore`) learned
this lesson when `claude-sonnet-4-20250514` sat past its retirement date
404-ing in production. As of 2026-08-04 this model is roughly 9 months old;
Anthropic has historically retired Haiku variants within 6–12 months of
introducing successors. If the model is retired, every call to
`/api/practice/generate-station` will fail with a 502 until manually updated.
**Fix:**
1. Verify the current model ID against the Anthropic API (no credits needed —
   `GET /v1/models`).
2. Add a `check:models` npm script (or reuse the one in escape-hatch-explore)
   to CI so retirement is caught before production.
3. Consider extracting the model ID to an env var
   (`ANTHROPIC_HAIKU_MODEL_ID`) so it can be updated without a deploy.

## Low

### L-2 · No Content-Security-Policy header — carry-over
**File:** `next.config.ts`
**Status:** Not fixed. `X-Frame-Options`, `X-Content-Type-Options`, and
`Referrer-Policy` are set, but there is no CSP.
**Fix:** Add a `Content-Security-Policy` header. At minimum:
```
default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob: https://i.scdn.co; connect-src 'self' https://api.spotify.com;
```
Tune `'unsafe-inline'` out of `script-src` once inline scripts are inventoried.

### L-3 · `storage.ts` localStorage helpers are stale — carry-over
**File:** `src/lib/storage.ts`
**Status:** Not fixed. `loadRoster` / `saveRoster` have no callers in
production code. `addHistoryEntry` and `clearAbsences` are still used in
`page.tsx` as pure data-transformation helpers, but the module also carries
dead localStorage code that is never reached.
**Fix:** Extract `addHistoryEntry` and `clearAbsences` into `lib/roster-utils.ts`
as pure functions; delete `src/lib/storage.ts`.

### L-4 · No test suite — carry-over
**Status:** Not fixed. The scheduler and constraint logic are pure functions
with complex behaviour. No unit tests exist.
**Fix:** Add Vitest. Start with the scheduler's bench schedules and
backtracking edge cases (11-player playoff mode, 13-player, infeasible
constraints hitting the 10-second budget).

### L-7 · `/api/admin/users` GET is unbounded — NEW
**File:** `src/app/api/admin/users/route.ts:22-38`
**Status:** New finding.
**Detail:** The admin user list query has no `.limit()`. At current scale
(handful of coaches) this is harmless, but will degrade as user count grows.
**Fix:**
```typescript
const allUsers = await db
  .select({ ... })
  .from(users)
  .limit(500); // add pagination if the admin panel ever grows beyond ~100 users
```

### L-8 · `spotify-status` leaks service account Spotify user ID to all authenticated users — NEW
**File:** `src/app/api/auth/spotify-status/route.ts:14-19`
**Status:** New finding.
**Detail:** The endpoint returns `serviceUserId` (the Spotify user ID string of
the app-owner's service account) to any user who holds a valid session,
including pending users (there is no approval gate). This is not an
authentication bypass — the Spotify user ID is semi-public — but it is
inconsistent with the rest of the API surface and leaks an implementation
detail unnecessarily.
**Fix:** Either omit `serviceUserId` from the response (only `configured` +
`linked` are needed by the client), or add the standard approved/admin gate.
The simplest fix is to drop `serviceUserId` from the JSON:
```typescript
return NextResponse.json({ configured, linked: !!serviceUserId });
```

### L-9 · `teams/[id]/route.ts` DELETE counts teams via full row fetch — NEW
**File:** `src/app/api/teams/[id]/route.ts:100`
**Status:** New finding.
**Detail:**
```typescript
const count = await db.select({ id: teams.id }).from(teams).where(eq(teams.userId, userId));
if (count.length <= 1) { ... }
```
This fetches every team row for the user into memory just to check the count.
Should use an aggregate.
**Fix:**
```typescript
const [{ count }] = await db
  .select({ count: sql<number>`count(*)::int` })
  .from(teams)
  .where(eq(teams.userId, userId));
if (Number(count) <= 1) { ... }
```

## Performance notes (no action required now)

- **`getValidServiceAccessToken` makes two sequential DB reads per call**
  (`getAppSetting` for the refresh token, then config inside `refreshAccessToken`).
  On high-traffic routes both reads could be batched, but at current scale
  this is fine.
- **N+1 Spotify searches in `sync-playlist`**: for each present player without
  a walk-on song, the loop tries up to 15 sequential `findCleanTrack` calls.
  With a 10-player roster of unassigned songs, worst case is ~150 serial Spotify
  API requests. Acceptable at one sync per game per team.
- **`isAdmin` makes 2 DB round trips per call** in routes that subsequently
  also call `getUserId` or `getUser` — e.g. admin PATCH calls `isAdmin` (1 DB
  call) then `getUserId` again to check self-demotion. Could be refactored to a
  single `SELECT` that returns both identity and role.
