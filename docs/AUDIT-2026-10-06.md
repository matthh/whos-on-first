## Findings

### Medium — M-1 (carry-forward): `logoDataUrl` unbounded in roster PUT API

**File:** `src/app/api/roster/route.ts:112-113`

The roster `PUT` route accepts and stores `config.logoDataUrl` without any size validation. The Onboarding UI enforces a 2 MB client-side cap, but a direct API caller can POST an arbitrarily large base64 string. This was first logged in AUDIT-2026-09-22 and remains unresolved.

**Recommended fix:** In the PUT handler, after `config !== undefined` is confirmed, add:
```ts
if (typeof config?.logoDataUrl === "string" && config.logoDataUrl.length > 3_000_000) {
  return NextResponse.json({ error: "Logo too large (max ~2 MB)" }, { status: 413 });
}
```
(Base64 inflates by ~33 %, so 3 MB base64 ≈ 2.25 MB raw; adjust the cap as needed.)

### Medium — M-2 (carry-forward): No rate limiting on expensive third-party endpoints

**Files:** `src/app/api/spotify/sync-playlist/route.ts`, `src/app/api/practice/generate-station/route.ts`

Both routes make outbound calls to paid third-party APIs (Spotify, Anthropic) with no per-user throttling. An approved coach can call either endpoint in a tight loop, generating unbounded Spotify API quota consumption and Anthropic billing. Reported in prior audits; still open.

**Recommended fix:** Add a simple time-window check in each handler (e.g., store last-called timestamp in the DB or use Vercel's KV, refuse if called more often than once per 10 seconds per user). Alternatively, add Vercel rate-limit middleware.

### Low — L-1 (carry-forward): Google OAuth name not sanitized on insert/link

**File:** `src/app/api/auth/google-login-callback/route.ts:95`

`const name = profile.name || null` is stored verbatim from Google's token response — no HTML stripping, no length cap — inconsistent with every other name-write path in the codebase. The actual XSS risk is low (React escapes output) but the inconsistency is a defence-in-depth gap and was first flagged in AUDIT-2026-09-22.

**Recommended fix:**
```ts
const rawName = profile.name || null;
const name = rawName ? rawName.replace(/<[^>]*>/g, "").slice(0, 100) : null;
```
Apply to both the `insert` (new user) and `update` (link existing) paths on lines 127 and 130.

### Low — L-2 (carry-forward): Dead code — `getValidAccessToken` and legacy per-coach Spotify routes

**File:** `src/lib/spotify.ts:182-215`

`getValidAccessToken(userId)` is exported but never imported anywhere (confirmed by grep). The per-coach OAuth connect/callback routes still write tokens to `users.spotifyAccessToken` / `users.spotifyRefreshToken` but no route reads them for outbound calls — the service-account flow superseded this entirely.

This dead code increases maintenance surface and could confuse future contributors into thinking per-coach OAuth is still active.

**Recommended fix:** Remove `getValidAccessToken`, `/api/auth/spotify-connect`, and `/api/auth/spotify-callback` routes in a dedicated cleanup PR. Keep the `users.spotifyAccessToken` / `users.spotifyRefreshToken` columns until data migration is confirmed safe, but stop the callback writing to them (or make the callback a 410 redirect to avoid accidental re-OAuth).

### Low — L-3 (carry-forward): No Content-Security-Policy header

**File:** `next.config.ts`

`X-Frame-Options`, `X-Content-Type-Options`, and `Referrer-Policy` are set but no CSP header is present. Without CSP, any future reflected-XSS would have no second line of defence. The app's own XSS mitigations are sound, but adding a restrictive CSP is a standard hardening step.

**Recommended fix:** Add a CSP header to the `headers()` block in `next.config.ts`. A tight baseline for a Next.js app:
```
default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'; img-src 'self' data: https:; connect-src 'self' https://api.spotify.com https://accounts.spotify.com https://api.resend.com; frame-ancestors 'none';
```

### Low — L-4 (carry-forward): AI model ID (`claude-haiku-4-5-20251001`) may silently go stale

**File:** `src/app/api/practice/generate-station/route.ts:86`

The model ID is hardcoded with no `check:models` script (unlike the `escape-hatch-explore` sibling project). If Anthropic retires the model, the endpoint starts returning 502s with no CI alert. This was documented in ARCHITECTURE.md tech debt item 7.

**Recommended fix:** Add a `check:models` npm script (see sibling project `escape-hatch-explore`) or add a periodic reminder comment to review the model ID. Minimum: add a code comment with the model's expected retirement date if known.

---

### Low — L-5: `spotify/search` query has no length cap

**File:** `src/app/api/spotify/search/route.ts:42-43`

The `q` query parameter is trimmed but not length-capped before being forwarded to Spotify's search API. An authenticated user could send a multi-megabyte query string. Spotify will almost certainly reject it, but this wastes server bandwidth and leaks request size to third-party logs.

**Recommended fix:** Cap `q` at a reasonable length (e.g., 200 chars) before forwarding:
```ts
const q = new URL(request.url).searchParams.get("q")?.trim().slice(0, 200);
```
