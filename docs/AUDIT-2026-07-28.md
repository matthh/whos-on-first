## Medium

### M-1 · `/api/practice/generate-station` does not check approved status — carry-over from 2026-07-14
**File:** `src/app/api/practice/generate-station/route.ts:47`
**Status:** **Not fixed.** `getUserId(request)` is called but not
`getUser` + approved/admin gate, so pending users can trigger Claude Haiku
calls at the app owner's expense.
**Fix:**
```typescript
import { getUserId, getUser } from "@/lib/auth";
// after getUserId check:
const user = await getUser(request);
if (!user || (user.status !== "approved" && user.role !== "admin")) {
  return NextResponse.json({ error: "Account not approved" }, { status: 403 });
}
```

### M-2 · No rate limiting on expensive third-party routes — carry-over from 2026-07-14
**Files:** `src/app/api/practice/generate-station/route.ts`,
`src/app/api/spotify/sync-playlist/route.ts`
**Status:** **Not fixed.** Both routes make outbound calls (Anthropic / Spotify)
without any per-user or global throttle. A single approved user can call them
in a rapid loop.
**Fix:** Add Vercel KV or an in-memory TTL counter (e.g. max 10 calls per user
per minute for generate-station, max 5 per minute for sync-playlist). Until KV
is wired up, a short `Date.now()`-based cooldown persisted in a module-level
`Map` provides a serverless-safe approximation for low-traffic deployments.

### M-3 · `logoDataUrl` stored without server-side size cap — carry-over from 2026-07-14
**File:** `src/app/api/roster/route.ts` (PUT handler, `config?.logoDataUrl`)
**Status:** **Not fixed.** Any base64 image payload can be written directly to
Postgres. The Onboarding UI caps uploads at 2 MB, but direct API calls bypass
this.
**Fix:** In the PUT handler, after extracting `config.logoDataUrl`, reject
strings longer than ~2,750,000 chars (~2 MB binary → base64 overhead):
```typescript
if (config?.logoDataUrl && config.logoDataUrl.length > 2_750_000) {
  return NextResponse.json({ error: "Logo too large (max 2 MB)" }, { status: 413 });
}
```

### M-5 · `role` and `status` not validated as allowed enum values in admin routes — NEW
**File:** `src/app/api/admin/users/route.ts:61-63` (POST), `route.ts:137-138` (PATCH)
**Status:** New finding.
**Detail:** Both the POST and PATCH handlers accept arbitrary strings for `role`
and `status` without checking against the allowed set. A typo or case mismatch
(`"APPROVED"` instead of `"approved"`, `"superadmin"` instead of `"admin"`)
writes an invalid value to the DB. All downstream role/status checks use exact
lowercase literals (`user.role === "admin"`, `user.status === "approved"`), so
any out-of-set value silently locks the user out or gives unexpected behaviour.
**Fix:** Add allowlist guards before the DB write in both handlers:
```typescript
const ALLOWED_ROLES = ["admin", "user"] as const;
const ALLOWED_STATUSES = ["pending", "approved", "suspended"] as const;

// POST / PATCH, before building `updates`:
if (role !== undefined && !ALLOWED_ROLES.includes(role)) {
  return NextResponse.json({ error: "Invalid role" }, { status: 400 });
}
if (status !== undefined && !ALLOWED_STATUSES.includes(status)) {
  return NextResponse.json({ error: "Invalid status" }, { status: 400 });
}
```

### M-6 · Spotify routes skip user approval gate — NEW
**Files:**
- `src/app/api/spotify/search/route.ts:34-36`
- `src/app/api/spotify/sync-playlist/route.ts:34-36`
- `src/app/api/auth/spotify-disconnect/route.ts:8-10`
**Status:** New finding.
**Detail:** All three routes call `getUserId(request)` but do not call
`getUser` + check `status === "approved"` or `role === "admin"`. A pending
user can:
- Search Spotify via the shared service account (consuming API quota).
- Trigger a full playlist sync: this reads the roster, writes default walk-on
  songs back to the `rosters` table (a roster mutation), and creates/updates a
  Spotify playlist using the service account.
- Disconnect their own Spotify tokens (low risk, but inconsistent policy).
**Fix:** Add the same approval gate used by roster/history/teams routes:
```typescript
import { getUserId, getUser } from "@/lib/auth";

const user = await getUser(request);
if (!user || (user.status !== "approved" && user.role !== "admin")) {
  return NextResponse.json({ error: "Account not approved" }, { status: 403 });
}
```
Apply to all three routes (can skip disconnect if preferred since it only
clears the caller's own tokens, but consistency is preferred).

### L-5 · `/api/history` GET is unbounded — NEW
**File:** `src/app/api/history/route.ts:19-24`
**Status:** New finding.
**Detail:** The query has no `.limit()`. A team that has been in use for a
full season could accumulate dozens of entries with large `players` JSON blobs;
all rows are returned in a single response. This is low risk today (rosters are
small and history is per-team) but will degrade as usage grows.
**Fix:**
```typescript
const entries = await db
  .select()
  .from(gameHistory)
  .where(and(eq(gameHistory.userId, userId), eq(gameHistory.teamId, team.id)))
  .orderBy(desc(gameHistory.createdAt))
  .limit(200); // reasonable cap; add pagination if needed later
```

### L-6 · `db.ts` uses a non-null assertion on `POSTGRES_DATABASE_URL` — NEW
**File:** `src/lib/db.ts:4`
**Status:** New finding.
**Detail:** `neon(process.env.POSTGRES_DATABASE_URL!)` suppresses the
TypeScript error but still throws a cryptic runtime exception if the env var is
absent. The established pattern in `session.ts` and `auth.ts` is to throw an
explicit named error.
**Fix:**
```typescript
const dbUrl = process.env.POSTGRES_DATABASE_URL;
if (!dbUrl) throw new Error("POSTGRES_DATABASE_URL not set");
const sql = neon(dbUrl);
export const db = drizzle(sql, { schema });
```

## Performance notes (no action required now)

- **`getValidServiceAccessToken` makes two sequential DB reads per call**
  (`getAppSetting` for the refresh token, then again inside `refreshAccessToken`
  for config). On high-traffic routes both reads could be batched, but at
  current scale this is fine.
- **N+1 Spotify searches in `sync-playlist`**: for each present player without
  a walk-on song, the loop tries up to 15 sequential `findCleanTrack` calls.
  With a 10-player roster of unassigned songs, worst case is ~150 serial Spotify
  API requests. At current scale (one sync per game per team) this is acceptable,
  but worth revisiting if the user base grows.
- **`isAdmin` makes 2 DB round trips**: it calls `getUser` internally, which
  issues a `SELECT`. Routes that subsequently call `getUserId` are efficient, but
  routes that call both `isAdmin` and then `getUser` again (e.g. admin PATCH
  calling `getUserId` to get `currentAdminId`) make two separate DB queries that
  could be one.
