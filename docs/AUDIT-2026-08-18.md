## High

### H-1 · Admin PATCH response leaks Spotify OAuth tokens — NEW
**File:** `src/app/api/admin/users/route.ts:159–170`

The PATCH handler calls `.returning()` without a column projection after
updating a user row. Drizzle's unqualified `.returning()` returns every
column, including `spotifyAccessToken` and `spotifyRefreshToken`. Any admin
client (browser or API caller) that inspects the JSON response body receives
live, usable Spotify refresh tokens for whichever user was edited.

This violates the stated invariant: *"Never select `spotifyAccessToken` /
`spotifyRefreshToken` in admin-facing queries."* The GET handler on the same
route already projects only safe columns (id, email, name, role, status,
authProvider, authProviderId, activeTeamId, createdAt, lastLoginAt,
spotifyUserId, spotifyDisplayName) — the PATCH handler must match.

The POST handler (create user, line ~79) has the same pattern, but newly-created
users never have tokens, so the exposure is lower severity there.

**Fix:** Add an explicit column map to `.returning()` in the PATCH handler (and
POST for consistency) mirroring the GET handler's safe field set:

```typescript
const [updated] = await db
  .update(users)
  .set(updates)
  .where(eq(users.id, id))
  .returning({
    id: users.id,
    email: users.email,
    name: users.name,
    role: users.role,
    status: users.status,
    authProvider: users.authProvider,
    authProviderId: users.authProviderId,
    activeTeamId: users.activeTeamId,
    createdAt: users.createdAt,
    lastLoginAt: users.lastLoginAt,
    spotifyUserId: users.spotifyUserId,
    spotifyDisplayName: users.spotifyDisplayName,
  });
```

The admin page's `User` interface only references id, email, name, role,
status, authProvider, createdAt, and lastLoginAt — the narrowed return value
is a drop-in replacement for the frontend.

## Medium

### M-2 · No rate limiting on any API route — carry-over
**Files:** `src/app/api/**`

No rate-limiting middleware exists. Every API route accepts unlimited request
volume. The Spotify sync-playlist and practice station generator routes are
particularly exposed — they proxy to third-party APIs (Spotify, Anthropic) on
every call with no throttling.

**Fix:** Add per-IP or per-user rate limiting (e.g. `@upstash/ratelimit` with
Vercel KV). Sync-playlist and generate-station should have tighter limits
(e.g. 5 req/min) than read-only roster/history endpoints (e.g. 60 req/min).

### M-3 · Logo data-URL accepted with no size cap — carry-over
**File:** `src/app/api/roster/route.ts` (PUT handler, `logoDataUrl` field, line ~112)

Team logos stored as base64 data URIs have no server-side maximum. An oversized
upload can bloat the database row and exceed Neon's request payload cap. The
Onboarding UI caps file selection at 2 MB, but the API itself enforces nothing.

**Fix:** Reject `logoDataUrl` values whose `length` exceeds ~270 000 characters
(approximately 200 KB of binary content after base64 overhead). Return HTTP 413.

### M-4 · `constraint_overrides` table is completely unused — carry-over
**File:** `src/lib/schema.ts`, `drizzle/0001_multi_team.sql`

The `constraint_overrides` table exists in the schema and migrations but is
never read by any route or UI component. It is dead weight at the DB layer.

**Fix:** Drop the table in a new migration and remove the schema definition,
or wire the overrides into the solver's constraint pipeline if the feature is
actually planned.

### M-7 · AI model ID hardcoded in source — carry-over
**File:** `src/app/api/practice/generate-station/route.ts:86`

`claude-haiku-4-5-20251001` is a literal string in the handler. When Anthropic
retires the model ID the endpoint will return 502 errors with no warning.
There is no `check:models` equivalent in this project.

**Fix:** Extract to a named constant (e.g. `PRACTICE_MODEL` in `lib/ai.ts`).
Consider adding a weekly CI step that calls the Anthropic models list endpoint
and verifies the ID is still active.

## Low

### L-2 · No Content Security Policy header — carry-over
**File:** `next.config.ts`

The app sets `X-Frame-Options`, `X-Content-Type-Options`, and `Referrer-Policy`
but no CSP. User-supplied content (team names, player names, logo data URIs)
is rendered in the DOM; any future `dangerouslySetInnerHTML` path would create
an XSS vector without a CSP backstop.

**Fix:** Add a CSP via `next.config.ts` headers or middleware. At minimum:
`default-src 'self'; img-src 'self' data:; script-src 'self' 'unsafe-inline'`
(tighten as app-specific sources are inventoried).

### L-3 · `storage.ts` is dead code — carry-over
**File:** `src/lib/storage.ts`

`loadRoster` / `saveRoster` (localStorage) are no longer called from
production code. The module is still imported by `page.tsx` only for
`addHistoryEntry` and `clearAbsences`, which are pure-logic helpers that do
not themselves touch localStorage. The localStorage code paths in those helpers
are never reached.

**Fix:** Extract `addHistoryEntry` and `clearAbsences` as pure functions into
`lib/history-helpers.ts` (or similar), then delete `storage.ts`.

### L-4 · No test suite — carry-over
**Files:** `src/lib/scheduler.ts`, `src/lib/constraints.ts`

The backtracking scheduler and constraint logic are pure functions ideal for
unit testing but have zero coverage. An edge-case constraint change could
silently produce invalid game sheets.

**Fix:** Add `vitest` and cover the scheduler with scenario tests: minimum
bench minutes, max-per-week caps, playoff mode bench ordering, avoid-positions
post-pass.

### L-5 · `coachName` field in roster PUT has no validation — NEW
**File:** `src/app/api/roster/route.ts:121–123`

The `coachName` field accepted by the PUT handler is written directly to
`users.name` with no length cap or HTML stripping. Player names on the same
endpoint are limited to 50 characters and stripped of HTML tags, but
`coachName` is not. A sufficiently large value could bloat the DB row; an
HTML string would not be executed (the admin page renders it as text) but is
inconsistent with the validation pattern applied elsewhere.

**Fix:** Apply the same guard used for player names:
```typescript
if (coachName !== undefined) {
  const safe = String(coachName).replace(/<[^>]*>/g, "").slice(0, 100);
  await db.update(users).set({ name: safe }).where(eq(users.id, userId));
}
```

### L-7 · `/api/admin/users` GET returns unbounded result set — carry-over
**File:** `src/app/api/admin/users/route.ts` (GET handler)

The admin user list query has no `.limit()`. Low risk at current scale but will
degrade as users grow.

**Fix:** Add cursor-based pagination or a hard `.limit(500)` with a documented
maximum.

### L-8 · `/api/auth/spotify-status` unnecessarily exposes `serviceUserId` — carry-over
**File:** `src/app/api/auth/spotify-status/route.ts:16`

The response body includes the Spotify service-account user ID. This value is
not used by any known client for display or routing — it leaks an internal
identifier to all authenticated users unnecessarily.

**Fix:** Omit `serviceUserId` from the response. Return only `{ configured, linked }`.

### L-9 · Teams DELETE count-check fetches full rows — carry-over
**File:** `src/app/api/teams/[id]/route.ts:100`

```typescript
const count = await db.select({ id: teams.id }).from(teams).where(eq(teams.userId, userId));
if (count.length <= 1) { … }
```

This loads every team row for the user to count them. Use `COUNT(*)` instead.

**Fix:**
```typescript
const [{ n }] = await db
  .select({ n: sql<number>`count(*)::int` })
  .from(teams)
  .where(eq(teams.userId, userId));
if (n <= 1) { … }
```

### L-10 · Middleware HMAC comparison should use `crypto.subtle.verify` — carry-over
**File:** `src/middleware.ts:43–48`

The edge middleware computes the expected HMAC with `crypto.subtle.sign`, then
compares base64url-encoded strings character-by-character in a manual loop.
The loop does not short-circuit, so it is functionally constant-time for
same-length strings. However, comparing string encodings rather than raw bytes
is non-idiomatic and would become timing-vulnerable if the encoding were
changed. The cleaner, idiomatic fix uses `crypto.subtle.verify` which
internally performs a constant-time comparison on the raw bytes and removes the
manual loop entirely:

```typescript
const hmacBytes = Uint8Array.from(
  atob(hmac.replace(/-/g, "+").replace(/_/g, "/")),
  c => c.charCodeAt(0)
);
const valid = await crypto.subtle.verify(
  "HMAC", key, hmacBytes, new TextEncoder().encode(payload)
);
if (!valid) return null;
```
